# GhostDeploy 0.3.0a1

**Public Alpha · Experimental · Staging evaluation only. Do not use in production.**

GhostDeploy helps independent developers deploy reviewed custom addon changes to self-hosted Odoo. This first public Alpha is intended for disposable evaluation with synthetic data and independent feedback. It requires no centralized GhostDeploy service or subscription.

## Compatibility and installation

The target is Ubuntu, Python 3.11+, one direct systemd-managed Odoo 18.0 or 19.0 service, PostgreSQL with matching native client tools, Git and a full custom addon checkout. The hosted combined tests used Ubuntu 24.04 and PostgreSQL 16.16. OpenSSH and a dedicated deployment identity are required for GitHub Actions deployments.

Use the versioned wheel and check it against the supplied `SHA256SUMS` before installation. The source distribution includes the staging validation kit. Follow the [Quick Start](https://github.com/UsamaFathi/GhostDeploy/blob/main/docs/quick-start.md) and [installation, upgrade and uninstall instructions](https://github.com/UsamaFathi/GhostDeploy/blob/main/docs/installation.md).

## Capabilities and safeguards

- Guided setup, read-only diagnostics, and plans that show the exact commit and candidate database changes.
- Clean checkout and trusted branch checks, explicit database allowlists and upgrade approval. The systemd restart affects every served database, and shared addon code can affect databases outside the allowlist.
- Private PostgreSQL and filestore backups verified before upgrades, a per-service deployment lock, and a durable journal that blocks retries after partial failure. Recovery is manual.
- Generated GitHub Actions workflow with pinned host verification, a restricted SSH gateway, deployment concurrency and remote failure propagation. Administrators control host configuration, scoped sudo and GitHub environment rules. Approved addon code is trusted application code. [Architecture](https://github.com/UsamaFathi/GhostDeploy/blob/main/docs/architecture.md) · [Security](https://github.com/UsamaFathi/GhostDeploy/blob/main/SECURITY.md)

## Limitations and feedback

Plan a maintenance window and review compatibility of all databases on the service. Schedule a matching database and filestore restore drill. Systemd and optional HTTP probes check service availability. Use authenticated application checks for business-level validation. Parallel writers outside the managed service can compromise backup consistency. The Alpha supports a single service and conservatively blocks risky changes such as addon removal and dependency changes. [Operations](https://github.com/UsamaFathi/GhostDeploy/blob/main/docs/operations.md)

Independent testers can follow the [staging kit](https://github.com/UsamaFathi/GhostDeploy/blob/main/validation/staging/README.md) on an explicitly authorized disposable Ubuntu host and submit sanitized results through the [Alpha validation issue form](https://github.com/UsamaFathi/GhostDeploy/issues/new?template=alpha-validation.yml). Use [GitHub Issues](https://github.com/UsamaFathi/GhostDeploy/issues) for ordinary bugs and the [private security reporting procedure](https://github.com/UsamaFathi/GhostDeploy/blob/main/SECURITY.md) for suspected vulnerabilities.
